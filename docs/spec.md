# ТЗ: сервис сопроводительной ведомости и бронирования оборудования

Oct 16, 2026 · @Kirill

## Цель и фазы

Сервис для лаборатории: сначала электронная сопроводительная ведомость партий через Telegram-бот, затем бронирование оборудования поверх тех же данных.

- **Фаза 1 (MVP)** — ведомость. Технолог описывает маршруты и операции, операторы с телефона записывают параметры каждой операции для каждой партии, данные выгружаются для сравнения и анализа. Ведомости сейчас нет, её только планируют вести в Word/Excel.
- **Фаза 2** — бронирование оборудования вместо общей Яндекс Таблицы. Использует сущности фазы 1 (User, Operation, Route, Batch).

Проект учебный: цель — освоить Python backend на реальной задаче. Код пишет автор.

## Пользователи и роли

Четыре роли по иерархии: вышестоящая роль имеет все права нижестоящих. Одна роль на пользователя.

| Role | Может |
| --- | --- |
| admin | всё, включая выдачу ролей и подтверждение новых пользователей |
| technologist | заводит оборудование, операции, параметры, маршруты (в фазе 1 — через код) |
| engineer | создаёт партии; в фазе 2 — маршруты; управляет бронями своих студентов |
| student | создаёт партии и заполняет операции; в фазе 2 — бронирует |

- У студента один руководитель-инженер (`supervisor_id`).
- Исключение из иерархии: переназначать оператора операции могут создатель партии, сам оператор и admin. Technologist и engineer — нет.

**Регистрация**

1. Человек нажимает Start, бот спрашивает имя.
2. Пользователь создаётся со статусом `pending` и ничего не может делать.
3. Admin получает сообщение с кнопками «Одобрить» / «Отклонить» и выбором роли.
4. Человеку приходит ответ.

Первый admin задаётся в `.env` (`ADMIN_TELEGRAM_ID`): при Start с этим id пользователь сразу создаётся как `admin`, `active`. Ушедших людей не удаляют, а ставят `blocked`, чтобы старые ведомости сохраняли авторов.

## Сущности фазы 1

Восемь сущностей. Ключевая идея: Route — общий шаблон, а у каждой партии своя копия этапов (BatchStep), поэтому правка шаблона не ломает старые ведомости, а отклонения в отдельной партии видны.

| Entity | Что это | Поля | Связи |
| --- | --- | --- | --- |
| User | человек | `name`, `telegram_chat_id`, `role`, `status` (`pending` / `active` / `blocked`), `notifications_enabled` | `supervisor_id` → User |
| Operation | тип операции: «отжиг», «отмывка» | `name`, `no_pause_after` | много Parameter |
| Parameter | что записывать в операции | `name`, `unit`, `type`, `min_value`, `max_value` | → Operation |
| Route | шаблон маршрута | `name` | много Step |
| Step | позиция операции в шаблоне | `order` | → Route, → Operation |
| Batch | партия, идущая по маршруту | `name` (генерируется), `comment`, `status` (`active` / `completed`), `sample_count`, `created_at` | → Route, `created_by` → User, много BatchStep |
| BatchStep | этап, реально выполняемый в партии | `order` | → Batch, → Operation, `operator_id` → User |
| ParameterValue | записанное значение | `value`, `recorded_at` | → BatchStep, → Parameter, `recorded_by` → User |

- Имя партии: `<дата>_<основной оператор>`, при совпадении сервис добавляет `.1`, `.2`. Имя уникально.
- Параметры хранятся строками (Parameter + ParameterValue), а не колонками: новый параметр добавляется без изменения схемы базы.
- Equipment в фазе 1 не нужен.

## Функции фазы 1 (MVP)

Всё делается в Telegram-боте; маршруты, операции и параметры пока заводятся в коде.

1. **Регистрация** через Start с подтверждением admin.
2. **Создать партию**: выбрать маршрут, указать число образцов, необязательный комментарий. Имя генерируется, этапы копируются из шаблона в BatchStep.
3. **Назначить оператора** на каждую операцию при создании партии.
4. **Переназначить оператора** — создатель партии, сам оператор или admin.
5. **Выбрать активную партию** из списка, если их несколько.
6. **Мои операции** — список операций, назначенных пользователю, по всем партиям.
7. **Заполнить операцию**: после выбора бот спрашивает параметры по очереди («Температура?» → 23 → «Влажность?» → 45 → «Записано»).
8. **Посмотреть и исправить значения**, пока партия `active`.
9. **Закрыть партию** вручную; после `completed` ведомость заморожена.
10. **Выгрузить ведомость** в Excel: одну партию и все партии маршрута.

## Правила и валидация

Данные идут в сравнение и анализ, поэтому значения — только числа в единицах параметра.

- Бот принимает только число; на текст отвечает «введи число».
- Значение вне `min_value`…`max_value` не принимается.
- Исправление перезаписывает значение и обновляет `recorded_by`, `recorded_at`. Полная история правок — позже.
- После `completed` значения партии менять нельзя.
- Нарушение `no_pause_after` (между операциями прошло время) — только предупреждение, не запрет.

## Уведомления

Все уведомления идут через бота и отключаются настройкой `notifications_enabled`.

- Admin: новый пользователь ждёт подтверждения.
- Пользователь: регистрация одобрена или отклонена.
- Оператор: ему назначена или переназначена операция.

Ограничение Telegram: бот не может написать человеку первым, пока тот не нажал Start. Поэтому назначать операции можно только зарегистрированным пользователям.

## Нефункциональные требования

Сервис работает на арендованном VPS за пределами России, потому что Telegram в России ограничен с марта 2026 и российский сервер может не достучаться до API Telegram. Пользователи работают через VPN.

- **Доступ**: только подтверждённые admin пользователи; первый admin — из `.env`.
- **Секреты** (токен бота, пароль базы) — только в `.env`, не в Git.
- **Бэкап**: автоматический дамп базы раз в сутки (`cron`), копия хранится вне VPS (Яндекс Диск или локальный HDD автора).
- **Проверка восстановления**: хотя бы один раз восстановить базу из бэкапа до начала реального использования.
- **Страховка интерфейса**: вся логика в сервисном слое, бот — только интерфейс. При проблемах с Telegram его можно заменить, например, мобильной web-формой.

Источник по Telegram: [Meduza, 17.03.2026](https://meduza.io/en/feature/2026/03/17/russia-was-expected-to-block-telegram-in-april-it-appears-to-have-done-it-two-weeks-early).

## Стек

Фаза 1 обходится без FastAPI: бот сам получает сообщения от Telegram. FastAPI появится в фазе 2 как второй интерфейс над тем же сервисным слоем.

| Слой | Инструмент |
| --- | --- |
| Интерфейс | `aiogram` (Telegram-бот) |
| Логика | сервисный слой на Python |
| Данные | SQLAlchemy, PostgreSQL |
| Migrations | Alembic |
| Выгрузка | `openpyxl` (Excel) |
| Развёртывание | Docker на VPS |
| Код | Git, GitHub |

Redis в MVP не нужен.

## Фаза 2 и отложенное

**Фаза 2 — бронирование**

- Новые сущности: **Equipment** (`name`, `description`, `instruction_url`, `status`: `working` / `broken` / `maintenance`, `restricted`, `sort_order`, таблица доступа `equipment_access`) и **Booking** (`start_time`, `end_time`, `status`: `confirmed` / `unconfirmed` / `cancelled`, `user_id`, `created_by`, необязательная связь с Batch). Слоты не хранятся — сетка строится из броней.
- Web-сетка «время × оборудование» с ручной бронью кликом по ячейкам; сервер запрещает пересечение броней на одном приборе.
- Бронь маршрута целиком: человек выбирает маршрут и время начала, сервис раскладывает этапы черновиком, человек сдвигает этапы, сервис проверяет и бронирует цепочку.
- Бронировать можно за любого; отменить могут владелец, создатель и вышестоящие.
- Сломанный прибор: брони не отменяются, отображаются серыми, владельцам будущих броней — уведомление; новая бронь — с предупреждением.
- Запрос подтверждения брони за сутки; без ответа бронь остаётся, но получает `unconfirmed`.
- Яндекс Таблица — не синхронизируется; сервис единственный source of truth, возможна read-only выгрузка.

**Отложено**

- Добавление параметров и маршрутов через бота (технологом).
- Полная история правок значений.
- Заполнение шаблона отчёта в Word.
- Личные и общедоступные шаблоны маршрутов (`is_public`).
- Загрузка файлов инструкций на сервер.
- Автоматический поиск свободных окон для маршрута.
